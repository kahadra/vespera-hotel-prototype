# 객실 상태와 연박 시스템

- 상태: `v2 IMPLEMENTED · REQUEST VALUES PROVISIONAL`
- 적용 시점: 5영업 압축 쇼케이스와 파생 캠페인·무한 영업 회색 상자
- 목적: 오늘의 투숙과 청소 판단이 다음 영업의 만족도·평판·현금과 객실 가용성을 바꾸게 한다.

## 1. 현재 권위: 단일 청결도

- 객실 상태는 `cleanliness` 하나만 `0~100`으로 영업 사이에 유지한다. 현재 데이터·상태·저장에는 `durability` 축이 없다.
- 새 손님에게 배정할 수 있는 기본 기준은 청결도 `40` 이상이다. 기준 미만의 빈 객실은 `청소 필요`로 막힌다.
- 이미 투숙 중인 연박 객실은 청결도가 기준 아래로 내려가도 손님을 강제로 옮기지 않는다. 다음 숙박 만족도에는 실제 청결도가 반영된다.
- 1박마다 손님의 `cleanliness_impact`와 데이터의 `wear_scale`로 청결도를 낮추고 `0~100` 범위에 고정한다.
- 청결도는 하드 제약 충족 여부와 별개인 만족도 원인이다. 유효 배치라도 낮은 청결도에서는 불만족과 등급별 평판 손실이 생길 수 있다.

현재 만족도 구간은 다음과 같다. 수치는 회귀 가능한 현 구현값이며 정식 밸런스 확정값은 아니다.

| 청결도 | 만족도 | 의미 |
| ---: | ---: | --- |
| 90~100 | 0 | 정돈된 객실 |
| 75~89 | -1 | 청소가 필요한 기색 |
| 50~74 | -3 | 눈에 띄게 정돈되지 않은 객실 |
| 0~49 | -6 | 방치된 객실 |

청결도 감점은 배치 선호 팁을 만들지 않고 내부 만족도에만 더한다. 같은 `-6` 불만족이라도 후기 평판 영향은 등급 가중치에 따라 N `-1`, R `-2`, SR `-4`, SSR `-7`이 될 수 있다.

## 2. 연박과 재방문

- `stay_nights=2`인 손님은 첫날 객실 ID와 남은 숙박 수를 저장한다.
- 다음 영업에 자동 포함되고 첫 객실을 유지하며 이동·회수·맞바꾸기 대상이 아니다.
- 만족도는 매일 실제 청결도, 주변 손님, 시설, 종족 시너지와 상극을 기준으로 다시 계산한다.
- 영업 결산은 방문 횟수, 직전 만족도, 최고 만족도를 기록한다.
- 이후 같은 손님이 새 예약으로 다시 방문하면 직전 만족도 `0/5/10` 구간에 따라 `+1/+2/+3`의 재방문 보너스를 받는다.

연박과 재방문은 구분한다. 연박은 하나의 예약이 이어지는 동안 객실을 잠그는 상태이고, 재방문은 이전에 끝난 투숙의 만족 기록을 새 예약에 반영하는 관계다. 연박 중 하루가 지났다는 이유로 방문 횟수나 재방문 보너스를 중복 지급하지 않는다.

## 3. 지배인의 선제 청소

- 결산 뒤 `영업 준비 / 공사 계약` 막간에는 빈 객실뿐 아니라 연박 중인 객실도 지배인이 선제 청소할 수 있다.
- 청소 1회는 현재 기본값 `8G`를 소비해 해당 객실의 청결도를 `100`으로 회복한다.
- 이미 청결도 `100`인 객실, 구조적으로 사용할 수 없는 객실, 같은 막간에 청소 요청을 거절한 객실은 청소할 수 없다.
- 연박 손님이 있다는 사실 자체는 청소 금지 사유가 아니다. 다만 해당 객실의 청소 요청이 열려 있으면 먼저 그 요청에 답해야 한다.
- 청소비는 형식 캠페인의 선지급 객실 정비비와 운영자금 보존식에 포함한다.

선제 청소는 손님 요청이 나오기 전에 위험을 없애는 확정 선택이다. 청소를 건너뛰면 즉시 무작위 세금을 내는 것이 아니라, 낮아진 청결도가 다음 숙박 만족도와 평판 위험으로 남는다.

## 4. 연박 객실 청소 요청

다음 값은 모두 `PROVISIONAL`이다.

- 후보는 현재 연박 중이며 실제 청결도가 `100` 미만인 객실만 사용한다. 깨끗한 객실이나 이미 끝난 체류는 후보가 아니다.
- 막간마다 시드 난수로 `35%` 확률을 한 번 검사하고, 요청은 막간 최대 1건만 연다. 현재 데이터 계약은 `max_per_intermission`을 정확히 `1`로만 허용한다.
- 같은 체류의 같은 손님은 한 번만 요청할 수 있다. 다음 막간에 다시 더러워져도 동일 체류 요청을 반복하지 않는다.
- 수락하면 현재 청소비 `8G`를 지불하고 청결도를 `100`으로 회복하며 호텔 평판 `+1`을 얻는다.
- 거절하면 호텔 평판 `-1`을 즉시 받고 더러운 상태를 유지한다. 거절 직후 같은 막간에는 그 객실을 다시 수동 청소할 수 없다.
- 요청을 수락할 현금이 부족하면 처리 완료로 보지 않는다. 요청과 체류 상태를 보존한다.
- 요청 여부·대상 선택은 같은 런 시드와 같은 막간 상태에서 재현돼야 한다.

요청은 아무 객실에 붙는 완전 무작위 비용이 아니다. 플레이어가 전날의 투숙과 선제 청소 선택으로 후보 자체를 줄일 수 있어야 한다.

## 5. 공사와 연박의 경계

- 같은 막간에서 `동관 증축`과 `시설·인테리어`를 분리해 각 최대 1건을 계약한 뒤 다음 영업으로 간다.
- 연박 중인 객실을 막거나 속성·동선·보너스를 직접 바꾸는 시설·인테리어는 손님이 퇴실할 때까지 계약할 수 없다.
- 이는 청소 금지가 아니라 객실 자체를 개조하는 공사의 잠금이다.
- 청소, 동관 증축, 시설·인테리어 중 어떤 것도 매번 강제 구매하지 않는다. 골드·다음 유지비·다음 객실 배정과 만족도 위험을 비교하게 한다.

## 6. 수직 증축과 예약 한도

- D열은 `F1-D → F2-D → F3-D` 순서로만 연다.
- 동관 증축은 객실 선택지를 넓히지만 상위 등급 수용의 필수 조건은 아니다.
- 기본 예약 응대 한도는 5명이며 완공된 동관 객실마다 1명씩 늘어난다. 사용 가능 객실 수는 시설 전환과 청결도 기준을 반영해 별도로 표시한다.
- 예약 단계의 `현재 객실도`에서 연박 손님의 고정 위치를 확인하되, 아직 도착하지 않은 사전 확정 손님에게는 객실을 미리 배정하지 않는다.
- 빈 이웃 객실 요청은 SR/SSR의 선택적 사생활 선호이므로, 증축을 하지 않아도 최소 하나의 유효 수용 부분집합이 남아야 한다.
- 시설·인테리어는 증축과 함께 누적 보유하고 객실 속성·관계·보너스를 합성한다.

## 7. 저장 계약

런 세이브 스키마 7은 다음 상태를 함께 보존·검증한다.

- 모든 객실의 정확한 `{ cleanliness }` 형상
- 마지막 마모 기록의 `guestId`, `roomId`, `cleanlinessLoss`, `cleanliness`
- 현재 연박 손님과 고정 객실
- 대기 중 청소 요청 또는 `null`
- 이번 막간의 요청 검사 완료 여부
- 이번 막간에 거절해 재청소가 막힌 객실 ID
- 같은 체류에서 이미 요청을 처리한 손님 ID

비형식 런의 구 스키마 3~6과 형식 캠페인 스키마 6은 스키마 7로 이관하며, 구 `durability` 값은 복원 축으로 유지하지 않고 제거한다. 형식 캠페인 스키마 3~5는 진행·재정 권위를 안전하게 추론할 수 없으므로 계속 거부한다.

## 8. 검증 게이트

- 데이터·초기 상태·저장 형상 어디에도 현재 권위인 `durability` 키가 남지 않는다.
- 낮은 청결도가 실제 만족도를 낮추고 같은 불만족이 등급별 평판 영향으로 변환된다.
- 연박 객실 선제 청소가 비용을 정확히 차감하고 청결도만 `100`으로 회복한다.
- 시드 요청은 더러운 연박만 고르고 막간 1건·동일 체류 1회를 지킨다.
- 수락과 거절의 비용·평판·청결도·같은 막간 재청소 제한이 저장·재개 뒤에도 동일하다.
- 청결도 압력만으로 예약 단계의 수용·거절 고민이 충분해졌다고 판정하지 않는다. 전원 수락 우월성은 별도 예약 압력 감사와 외부 플레이테스트에서 다시 평가한다.

## 9. 폐기한 이중 상태 제안

v1 뒤에는 청결도와 내구도를 별도 0~3 미터로 두고 빈 객실만 하루 2행동으로 청소·수리하는 안을 검토했다. 두 축의 역할 차이가 실제 선택보다 반복 정비와 저장 복잡도를 키웠고, 연박 객실을 손댈 수 없게 하면 플레이어가 위험을 관리하기보다 결과를 기다리게 된다는 문제가 있었다.

현재 권위는 단일 청결도, 연박 객실 선제 청소, 더러운 연박에 한정된 시드 요청이다. 과거 이중 미터 수치와 `투숙 중 정비 금지`는 구현 기준으로 사용하지 않으며, 변경 과정은 `29_DEVELOPMENT_CHRONICLE.md`에 기록한다.
