## 01. Codex를 어디에 사용했나요?

제가 직접 고안한 판타지 호텔 세계관, 종족 관계, CSP 객실 배정 코어 루프와 운영 밸런스를 실제 플레이 가능한 웹 게임으로 옮기는 데 Codex를 사용했습니다. 활용 범위는 설계 구조화, 기능 구현, 기술 문제 해결, 자동 검증과 제출 준비입니다. 저는 각 빌드를 직접 플레이하며 수정 우선순위와 최종 채택 여부를 결정했습니다.

설계 구조화: Codex는 제가 확정한 종족·등급·숙박 규칙·운영 흐름을 설계 문서와 JSON 데이터 구조로 정리했습니다.

구현과 기술 문제 해결: 외부 프레임워크 없는 HTML·CSS·JavaScript 게임과 UI를 구현하고, 상태 전환·입력·객실 배정 탐색에서 발생한 기술 문제를 수정했습니다.

검증과 제출 준비: Python 검산기와 CDP 기반 브라우저 자동 플레이를 구축하고, 실제 플레이 화면을 사용한 150초 데모 영상, 제출 썸네일과 정적 배포 ZIP을 제작했습니다.

## 02. 어떤 기능을 구현했나요?

제가 설계한 운영 구조를 바탕으로 Codex가 구현한 기능은 객실 배정, 호텔 운영, 성장과 발견의 세 축입니다.

객실 배정: 손님 수용·거절, 2분 체크인, 재배치 시간 비용, 드래그 전용 조작, 필수 숙박 조건과 선호 점수, 종족 시너지와 상극을 구현했습니다.

호텔 운영: 연박 객실 고정, 재방문 보너스, 객실 청결·내구도와 정비, 응대 한도와 실제 객실 여유의 분리, 예약 단계에서 기존 배치를 확인하는 객실도를 연결했습니다.

성장과 발견: 시간 제한 없는 튜토리얼과 5회의 개장 전 초청 영업, N·R·SR·SSR 등급, 시드 기반 손님·공사 제안, 결산 뒤 열람되는 숨은 선호, 순차 증축과 누적 시설·인테리어를 구현했습니다.

## 03. 어떤 문제를 해결했나요?

게임에서 해결할 문제와 해결 방향은 제가 정했고, Codex는 이를 안정적으로 작동시키는 구현상의 문제를 해결했습니다. 핵심은 복잡한 운영 규칙을 서로 충돌하지 않는 데이터·상태·입력·검증 체계로 옮기는 일이었습니다.

규칙과 상태: Codex는 제가 정한 필수 숙박 조건, 선호, 미열람 규칙, 숨은 선호의 정보 단계를 각각 독립된 데이터와 판정 로직으로 구현했습니다. 또한 제가 설계한 응대 한도, 사용 가능한 객실, 모든 필수 조건을 만족하는 배치 가능성의 구분도 서로 다른 값으로 구현해 과수용 위험이 실제 규칙으로 작동하게 했습니다.

입력과 성능: 손님 정보를 보려고 클릭했을 때 객실 배정이 바뀌던 문제는 클릭을 상세 열람으로 제한하고, 배정·교환·해제는 드래그로만 수행하도록 수정했습니다. 시간 만료 시 사용하는 긴급 배정 탐색에는 후보 축소, 부분 필수조건 가지치기, 우선순위 탐색과 실패 상태 캐시를 적용해 손님이 늘어나도 결과 화면으로 이어지도록 했습니다.

검증과 제출 안정성: 1024×720과 1280×720 전체 흐름을 자동 검사하고 강조 좌표와 영상의 실제 장면 변화를 검증하는 도구를 구축했습니다. 자동 수집한 감사 이미지는 제가 직접 확인하고 수정 여부를 결정했습니다.

## 04. 사람이 직접 결정한 부분은 무엇인가요?

제가 직접 설계한 핵심은 판타지 호텔 세계관과 종족 관계, CSP 사고를 익히는 객실 배정 코어 루프, 수용·투자·실패 사이의 운영 밸런스입니다. Codex는 이 설계를 데이터와 코드, UI로 구현하고 자동 검증했습니다.

세계관과 종족 관계: 베스페라 호텔이 정식 개장 전에 다양한 종족을 초대해 운영을 검증한다는 설정을 만들었습니다. 뱀파이어·수인·마녀·성기사의 동족 결속과 종족 간 상극, N·R·SR·SSR 등급별 위험과 보상이 객실 배치와 경영 선택에 직접 영향을 주도록 구성했습니다.

CSP 코어 루프: 손님의 조건을 읽고 수용 여부를 정한 뒤, 필수 조건을 만족하는 배치를 찾고 여러 가능한 답 중 선호 점수가 높은 선택을 비교하도록 설계했습니다. 결산에서 숨은 선호를 학습하고, 수익을 증축·시설·정비에 투자해 다음 영업의 조건을 바꾸는 흐름까지 하나의 루프로 연결했습니다.

운영 밸런스: 많이 받는 것이 항상 정답은 아니라는 원칙을 중심에 두었습니다. 거절보다 취소의 손실을 크게 하고, 제한 시간과 재배치 비용, 연박과 객실 마모, 응대 한도와 실제 배치 가능성의 차이를 통해 과수용과 안전한 운영 사이에서 판단하게 했습니다. Codex는 제가 정한 설계를 구현하고 기술 대안과 수치 후보를 제시했으며, 무엇을 채택·수정·제외할지는 제가 직접 플레이한 결과를 바탕으로 결정했습니다.

## 기존 프로젝트 활용 및 신규 개발 범위

챌린지 시작 시점의 실제 상태에 따라 아래 둘 중 하나만 사용한다.

### A. v1부터 챌린지 기간에 제작한 경우

> 본 프로젝트의 기획, 규칙, UI와 코드는 챌린지 기간 동안 제작했습니다. 초기 2회 영업 세로 단면을 먼저 만든 뒤, 같은 기간에 튜토리얼과 5회 진행, 시드 기반 손님·공사 제안, 연박·객실 상태·숨은 선호·종족 효과·증축·응대 한도를 갖춘 현재 v2로 확장했습니다.

### B. v1이 챌린지 이전부터 존재한 경우

> 기존 2회 영업 세로 단면(v1)과 기본 규칙 평가·테스트 기반을 활용했습니다. 챌린지 기간에는 5회 진행 구조, 시드 기반 손님·공사 제안, N·R·SR·SSR 확장 콘텐츠, 연박과 재방문, 객실 상태와 정비, 종족 시너지·상극, 숨은 선호 열람, 누적 시설과 순차 증축, 객실 수 기반 응대 한도와 예약 객실도, 드래그 전용 조작을 새로 개발했습니다. 기존 자동 검증·영상·배포 도구는 v2 흐름에 맞게 확장하고 산출물을 다시 제작했습니다.
