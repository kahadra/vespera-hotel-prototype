# 손님 데이터 규격과 명단

- 상태: `v2 IMPLEMENTED`
- 현재 적용 범위: 튜토리얼 + 5영업 압축 쇼케이스
- 데이터 원본: `data/prototype_v1.json`이라는 파일명은 배포 호환성을 위해 유지하지만, 내용은 v2 스키마다.

## 1. 버전 기록

- `v1`: 뱀파이어·수인 6명과 2회 영업으로 배치·시설 선택을 검증했다.
- `v2`: 4종족·16명, N/R/SR/SSR, 연박·객실 마모, 종족 시너지·상극, 시드 제안과 숨은 선호를 포함한다.
- `v2 schema 3`: 유효 배치의 고정 평판을 제거하고 내부 만족도, 등급별 평판 영향, 공개 불호, 호텔 격차 관용과 결산 후기를 추가한다.
- `v2 schema 4`: 손님 규격은 유지하고 데이터 기반 런 종료 조건과 버전이 있는 실행 기록 계약을 추가한다.

v1의 2영업 명단은 이 문서 마지막에 설계 이력으로 보존하지만 현재 생성 풀이나 밸런스 기준으로 사용하지 않는다.

### 호텔 수용 관련 값

- 각 시나리오의 `capacity`는 증축 전 기본 예약 응대 한도이며 v2에서는 5다.
- `balance.booking_capacity_per_expansion_room`은 완공된 추가 객실 한 실당 늘어나는 응대 인원이며 v2에서는 1이다.
- 실제 사용 가능 객실 수는 손님 데이터가 아니라 완공 여부, 시설 전환, 청결·내구 상태와 연박 점유를 합성해 런타임에서 계산한다.

## 2. 손님 데이터 구조

| 필드 | 형식 | 설명 |
|---|---|---|
| `id` | string | 변하지 않는 내부 식별자 |
| `name` | string | 플레이어에게 표시할 이름 |
| `species` | enum | `VAMPIRE`, `BEASTKIN`, `WITCH`, `PALADIN` |
| `rank` | enum | 정확히 `N`, `R`, `SR`, `SSR` |
| `base_fee` | integer | 영업 성공 시 기본 숙박비 |
| `reject_reputation` | negative integer | 신청 단계 거절의 평판 변화 |
| `cancel_reputation` | negative integer | 수용 후 강제 취소의 평판 변화. 거절보다 절댓값이 크다. |
| `stay_nights` | integer | 확정 숙박 일수 |
| `stayover_locks_initial_room` | boolean | v2에서는 항상 `true`; 연박 중 첫 객실 고정 |
| `cleanliness_impact` | integer | 1박마다 적용할 청결 소모의 원자료 |
| `durability_impact` | integer | 1박마다 적용할 내구 소모의 원자료 |
| `hard_constraints` | array | 개인 필수 조건 확장 자리. v2 손님은 비워 둔다. |
| `soft_preferences` | array | 카드에 항상 공개되는 개인 선호 |
| `soft_dislikes` | array | 선택적 개인 불호 확장 자리. v2 표본은 등급 공통 불호를 사용한다. |
| `showcase_only` | boolean | 5회차 특별 초대처럼 시연 전용인 경우만 사용 |

손님 데이터에는 `hidden_*` 필드를 두지 않는다. 숨은 정보는 개인 예외가 아니라 종족×등급의 반복 학습 대상이어야 한다.

## 3. 등급 데이터

| 등급 | 색·기호 | 시연 최소 단계 | 최소 평판 | 평판 영향 | 호평 기준 | 공개 공통 규정의 역할 |
|---|---|---:|---:|---:|---:|---|
| N | 회색 `•` | 1 | 0 | 1 | 2 | 추가 필수·불호 없음 |
| R | 청색 `◆` | 2 | 4 | 2 | 4 | 같은 층 동행, 선호·불호 각 1개 |
| SR | 보라 `✦` | 3 | 8 | 4 | 7 | 소음 금지, 선호 1개·불호 2개 |
| SSR | 금색 `♛` | 5 | 18 | 7 | 10 | 소음 금지, 선호 2개·불호 3개 |

SR/SSR의 `양옆 객실 비우기`는 필수 규정이 아니다. 공간을 투자하면 높은 점수를 주는 공개 사생활 선호다. 확장을 하지 않으면 상위 손님을 절대 받을 수 없는 구조를 피한다.

아직 만나지 않은 등급의 공개 내용은 운영 수첩에서 `미열람 규칙`으로 표시한다. 해당 등급 신청이 처음 도착하면 등급 규정을 자동 열람한다.

### 정식판 등급 확장 경계

현재 v2 데이터와 검증기는 정확히 `N/R/SR/SSR` 네 등급을 사용한다. 정식 캠페인 데이터는 상위 확장 슬롯 `UR`을 추가한 `N/R/SR/SSR/UR`을 기준으로 설계하되, UR의 평판 영향·등장 확률·규정 수는 정식 경제 시뮬레이션 전까지 확정하지 않는다.

몽마 손님은 `N`과 `R` 등급으로 생성하지 않고 최소 `SR`부터 등장한다. 몽마는 타종족 손님이 이미 호텔을 이용할 때 꿈·정기 계약과 공명 효과의 의미가 생기기 때문이다. 회색 상자 선호 대역은 같은 영업의 타종족 투숙객을 `SR 2명 / SSR 3명 / UR 4명`으로 두며, 이는 하드 숙박 조건이 아니라 높은 보상을 여는 공개 선호다. 정확한 인원은 정식 객실 수와 예약 생성 시뮬레이션 뒤 교체한다.

등급 데이터에는 다음 만족도 필드를 둔다.

| 필드 | 설명 |
|---|---|
| `reputation_influence` | 호평·아쉬움 한 건이 호텔 평판에 주는 크기 |
| `reputation_influence_label` | 예약 카드에 표시하는 정성적 영향 설명 |
| `positive_satisfaction_threshold` | 내부 만족도가 호평으로 전환되는 기준 |
| `soft_dislikes` | 충족 시 내부 만족도를 낮추는 공개 불호 목록 |

`soft_dislikes`의 `ignored_at_prestige_gap`은 `호텔 평판 단계 - 손님 등급 단계`가 해당 값 이상일 때 그 불호를 만족도 계산에서 제외한다. 호텔 격차가 큰 낮은 등급 손님은 다수의 불호를 관용하지만, 하드 제약은 절대 무시하지 않는다.

## 4. 내부 만족도와 후기

내부 만족도는 손님별로 계산하고 재방문 기록, 평판과 영업 평가에 사용한다. 정확한 숫자는 플레이어에게 표시하지 않는다.

- `negative`: 만족도 0 미만, `아쉬움` 후기와 음의 등급 영향
- `neutral`: 0 이상 호평 기준 미만, `무난` 후기와 평판 0
- `positive`: 호평 기준 이상, `호평` 후기와 양의 등급 영향

결산 후기에는 손님 이름, 후기 단계, 주요 선호·불호 원인, 해당 등급의 평판 영향만 표시한다. 오토마타 접객은 모든 종족에게 동일하게 보장되는 세계관 전제이므로 서비스 직원 태도는 만족도 데이터에 포함하지 않는다.

## 5. 종족 데이터 구조와 숨은 선호

| 필드 | 설명 |
|---|---|
| `id`, `name`, `icon`, `color` | 종족 식별과 표시 정보 |
| `hard_constraints` | 모든 구성원이 공유하는 공개 필수 숙박 조건 |
| `soft_preferences` | 모든 구성원이 공유하는 공개 공통 선호 |
| `synergy_thresholds` | 호텔 내 같은 종족 인원에 따른 양수 시너지 |
| `hidden_preferences_by_rank` | N/R/SR/SSR별 종족 공통 숨은 선호 |

종족의 공개 규정도 첫 신청 전에는 `미열람 규칙`으로 표시한다. 손님 카드에는 종족과 등급 표식, 공개 개인 선호만 두고 공통 규정은 수첩에서 확인한다.

`hidden_preferences_by_rank`의 규칙은 다음 불변 조건을 지킨다.

- N은 빈 배열이다.
- R/SR/SSR에는 최소 하나의 숨은 선호가 있다.
- ID는 `VAMPIRE:R:QUIET`처럼 종족과 등급을 포함하며 전체 데이터에서 고유하다.
- 모두 양수 점수의 선택 사항이다. 필수, 배정 불가, 감점 형태는 금지한다.
- 해당 종족×등급 손님이 투숙을 마치고 결산될 때 같은 조합 전체에 열람된다.

## 6. v2 종족

| 종족 | 공개 필수 조건 | 공개 공통 선호 | 플레이 역할 |
|---|---|---|---|
| 뱀파이어 | 햇빛 객실 사용 불가 | 조용한 객실 | 어두운 객실 경쟁과 깊은 동선 |
| 수인 | 시끄러운 객실 사용 불가 | 햇빛 객실 | 같은 종족 이웃·같은 층 무리 구성 |
| 마녀 | 햇빛 객실 사용 불가 | 조용한 객실 | 층과 고립 공간 최적화 |
| 성기사 | 조용한 객실 사용 불가 | 햇빛 객실 | 높은 층과 같은 종족 행렬 구성 |

같은 종족 인원은 `synergy_thresholds`에 따라 만족 보너스를 만든다. 뱀파이어↔수인, 마녀↔성기사 같은 명시된 상극은 같은 층에 함께 있을 때 감점을 준다. 어떤 종족 조합도 필수 조건만으로 불가능해져서는 안 된다.

Queen Umbra는 5회차 쇼케이스 전용 SSR 특별 초대다. 이 초대는 일반 SSR 출현 확률이나 정식 게임의 영구 해금 상태를 바꾸지 않는다.

## 8. 연박, 마모, 재방문

- `stay_nights=2`인 손님은 다음 영업의 고정 손님이 되며 첫날 객실을 유지한다.
- 연박 객실은 다른 손님에게 배정하거나 정비할 수 없다.
- 주변 손님·시설·시너지·상극이 달라질 수 있으므로 만족도는 매일 다시 평가한다.
- 객실 청결·내구도는 매 영업 뒤 감소하며 운영 기준 미만이면 배정할 수 없다.
- 빈 객실은 `영업 준비 / 공사 계약` 화면에서 골드를 내 100/100으로 정비할 수 있다.
- 재방문 시 직전 만족도 `0/5/10` 구간에 따라 `+1/+2/+3` 보너스를 받는다.

## 9. 5영업 명단 생성

| 회차 | 구성 |
|---:|---|
| 1 | Lune, Morrow, Aru, Fen 고정; 모두 N |
| 2 | Lune·Aru 고정 + 시드 신청 4명; R 1명 보장 |
| 3 | Morrow 고정 + 시드 신청 4명; SR 1명 보장 |
| 4 | 시드 신청 4명; 평판·단계 잠금 적용 |
| 5 | 시드 신청 4명 안에 Queen Umbra SSR 특별 초대 포함 |

일반 신청은 평판 구간의 등급 확률과 단계 잠금을 함께 적용한다. 각 확률 행은 N/R/SR/SSR 합계가 100이어야 하며, 동일 시드·상태·제외 목록은 같은 명단을 만든다. 보장 등급과 특별 초대는 시연 전달을 위한 명시적 예외다.

## 10. v1 2영업 명단 보존 기록

v1은 Lune, Morrow, Lady Nox, Aru, Fen, Garr의 6명으로 시작했다. 첫 영업은 Lune·Morrow·Aru·Fen 고정, 두 번째 영업은 네 신청자를 비교하고 방음 객실·라운지·비밀 통로 중 하나를 고르는 구조였다. 이 명단은 수용·거절과 관계 변경 시설을 검증한 출발점이며, v2에서는 네 등급과 더 큰 신청 풀로 확장되었다.

v1에서 상위 손님의 빈 이웃 객실 요청을 강한 규칙으로 시험한 기록은 폐기했다. v2에서는 같은 판타지를 오직 양수 점수의 선택적 사생활 선호로 사용한다.

## 11. 데이터 검증 조건

- 모든 ID는 고유하고 종족·등급·객실·시설·개선 참조가 존재한다.
- 등급 집합은 정확히 N/R/SR/SSR이고 확률 행의 합은 100이다.
- 취소 손실은 거절 손실보다 크다.
- 모든 손님은 숙박 일수, 객실 고정, 청결·내구 영향 값을 가진다.
- 손님 객체에는 개인 `hidden_*` 항목이 없다.
- 종족×등급 숨은 선호는 지원되는 soft 연산자, 고유 ID, 양수 점수를 가진다.
- 5개 시나리오는 1~5단계를 한 번씩 가지며 R·SR 보장과 SSR 특별 초대를 검증한다.
- `F1-D → F2-D → F3-D` 증축 선행조건을 지키고, 증축 없이도 최소 하나의 유효 수용 부분집합이 존재한다.
